## 1. 拒绝推断的结果在哪里看

**结果页顶部「仿真环境与可信度」卡片**——前提是配置页选了「拒绝推断（L0b）」环境。展开后是每个策略 swap-in 客群的「估计坏账 / 真实坏账 / 偏差 / 相对误差」。

它**不会**改写 L1–L5 的指标。这是刻意的：L2 的坏账率是"真值"（合成账簿全员有标签），拒绝推断的输出是"如果你在生产环境只能估，你会估成什么样"。两个数放在一起才有意义，混在一起反而没法看。

💭 **一个待决策的产品问题**：要不要在 L2 加一列「生产可得估计」——即把 swap-in 客群的坏账替换成推断值后重算通过率/坏账/RAROC，与真值并排。这会让"方法误差最终影响了哪个决策数字"一眼可见，但也让 L2 的表变宽。我倾向做，作为一个开关。

## 2. 策略对比：从描述两套配置，改成解释结果 ✅

原「策略对比」= AI 拿两套策略定义写一段描述。它回答"两套策略长什么样"，而人要问的是"差异解释了结果里的哪部分"。

本轮做了 **Swap-set 归因**，放在 L4 面板四象限下方：

- 规则差异清单（cutoff 680→650、DTI 0.60→0.68、MOB 12→6 …）
- **换入归因**：挑战者批了、冠军拒了——冠军是凭哪条规则拒的，每条规则的户数、占比、坏账率
- **换出归因**：反过来，挑战者凭哪条规则拒掉了冠军批的人
- 换入/换出客群各自的 **RAROC**（按准入方的定价算）

默认样本实测（v2.3 vs v2.2）：

| 换入原因（冠军的规则） | 户数 | 占比 | 坏账率 |
|---|---|---|---|
| 风险评分不足（旧模型 cutoff） | 16,442 | 84% | 2.32% |
| 近期逾期记录（MOB 12 → 6） | 2,599 | 13% | 1.77% |
| 负债率过高（DTI 0.60 → 0.68） | 503 | 3% | 2.19% |

| 换出原因（挑战者的规则） | 户数 | 占比 | 坏账率 |
|---|---|---|---|
| 风险评分不足（新模型） | 2,785 | 100% | 5.17% |

**读法**：v2.3 的收益 84% 来自模型重训（新模型把旧 cutoff 拦下的人重新排序），只有 16% 来自政策放宽；而它换出的人 100% 是新模型识别出的高风险客户。这是「模型升级」的证据，不是「政策放松」的证据——两者的上线审批路径完全不同。

AI 的对比端点（`/api/ai/compare/stream`）现在拿到的 facts 也包含这张归因表和红线报告，不再只看策略定义。

原独立「策略分析」页保留为静态的规则 diff 视图（评审材料用）。🔜 下一轮可把它降级为 L4 归因卡片的"查看完整定义"链接。

## 4.5 P5 执行结果（本轮）

清单上的 8 项全部落地。

### 缺陷根治

**1. 合成账簿加了时间轴** —— 这是 L3「零信息」问题的根治。每个账户新增四列：
`book_month`（放款月 0–11）、`default_mob`（第几个月违约）、`dpd_stage`（最坏逾期阶段）、
`first_dpd_mob`（首次 30dpd 的月份）。于是：

| 指标 | 之前 | 现在 |
|---|---|---|
| Vintage 曲线 | `bad_rate × logistic(m)` 画出来的 | 逐月累计真实违约占比，末点必然等于 MOB12 坏账率 |
| 迁徙率 | `0.52 + bad_rate × 3.5` | 曾 30dpd 的占比 → 其中转 60dpd 的占比 → 其中转 90+ 的占比，真条件概率 |
| FPD | `bad_rate × 0.32` | 首期即逾期的真实占比，且按放款月分组出真趋势 |
| PSI | 固定基数 + 噪声 | 各放款月核准客群的评分分布 vs 首月，真 PSI |
| CSI | 两次不同 seed 生成的数据对比 | 上半年 vs 下半年队列，覆盖全部评分卡输入 |

漂移做成**围绕年中对称**：月度间有真实漂移（PSI 随月份累积到 0.03–0.04），
但账簿整体风险不变，所以所有标定过的准入线和文档里的数字都不动。
`derived` / `simulated_cohorts` 标记现在会随数据自动判定——上传数据集没有时间轴，
仍然走旧的推导路径并被标注。

**2. L2 补了规模化数字**：核准户数、增量余额、总利润、总预期损失、占用资本，
前端新增一张"规模"表。v2.3 vs v2.2 在默认账簿上：利润 2,520 万 vs 720 万，
预期损失 142 万 vs 43 万，占用资本 1,463 万 vs 509 万。

**3. 指标归位**：`reason_coverage` 移到 L2（L5 保留一版并标注 `reason_coverage_moved_to`）；
L4 分数段补上每段的换入/换出户数与坏账；reslice 限流 30/min → 90/min。

**4. 新红线** `rank_ordering_broken`：模型分十分位出现坏账倒挂时警告。
AUC 看不出这个问题，但准入线正好落在倒挂分段上时，切分依据就是错的。

### 显性 AI

**5. 增量来源分解**（L4 四象限上方）—— 从归因表算出来的一句话结论：

> 增量的 84% 来自模型区分度提升（被旧模型评分拦下、被新模型重新排序的客群），
> 只有 16% 来自政策放宽；换入客群坏账 2.34%，换出客群坏账 4.28%，即多批的比拒掉的更干净。
> **这条路径按模型升级审批，不按政策放松审批。**

最后一句是这个功能存在的理由：同一个"通过率翻倍"，走模型审批还是走政策审批，
是完全不同的两件事。判定阈值是 60%，分不出主导时它会说"分不出"。

**6. 红线 → 一键找修复**：可修复的红线旁边出现按钮，点了会以当前取值为中心
向外搜索阈值、逐个真跑、逐个过红线，返回**最近的**不触线取值。

搜不到时它不沉默，而是诊断原因。v2.4-Beta 的 DI 问题实测：

> 搜索范围内没有任何阈值能清除该红线——这不是阈值问题，是策略结构问题：
> 该群体被拒的主因是「薄文件/行为不足」，占其拒绝原因的 99%，比参照群体高 99.3pp

调通过率从 45% 到 86%，年轻客群 DI 始终在 0.50–0.57。**这是对的答案**：
问题出在薄文件门槛，不在准入线。

**7. 评审包**（可信度卡片底部）—— 一键生成上线评审材料，八节：配置 / 核心指标 /
增量来源分解 / 红线 / 稳健性 / 拒绝推断误差 / **本材料未回答的问题** / 证据链。

它会**表态**，而且永远不会说"可以上线"：
- 有阻断红线 → 不可推进
- 多种子排序翻转 → 不可推进
- 没做复现 → 证据不足
- 都过了 → 可提交人工评审（附环境适用边界）

第 7 节是刻意设计的：大多数评审材料不写"我没回答什么"，这正是它们被轻易放行的原因。

顺带发现一件事：默认账簿上**冠军 v2.2 自己**在 18-25 岁客群的 DI = 0.796，本来就触线。
所以默认配置的评审包结论是"不可推进"。一个会放行这种情况的工具，本身就是问题。

**8. Critic 主动横比拒绝推断方法**：拒绝推断环境下，Agent 在审稿前自动跑
`compare_ri_modes`，把"你用的方法不是误差最小的那个"写进审稿意见。

## 5. Agent 不只是解释：按前沿产品的设计

你的理解对了一半——**在 UI 里**，Agent 之前确实只有解释能力，因为闭环只暴露在 API。本轮加了「Agent 调查」页，它现在能做的是：提一个问题 → 自己设计实验 → 真跑 → 过红线 → 做复现 → 对自己挑刺 → 结论写回注册表。每个 run 可点开。

这是起点。下面是 Agent 在这个产品里应该长成的样子，按优先级：

### 5.1 调查（Investigator）✅ 已有，需要打磨
**一句话 → 一份带证据链的答案。** 关键不在于 LLM 有多聪明，在于三个硬约束：预算在工具层强制、红线不可推翻、复现不稳就判 not_supported。这三个约束让它的输出可以被审计。

✅ P5 已补：Critic 在拒绝推断环境下主动横比方法。🔜 剩余打磨点：Designer 用真模型时限制"一次只动一个变量"。

### 5.2 评审包（Evidence Bundle）✅ 已交付（P5）
**策略上线评审需要的一切，一键打包**：候选 run 及其 manifest、红线报告、多种子复现、RI 方法误差、归因表、审稿意见、以及**没做的实验清单**。

它是这个平台跟"回测工具"的真正分界线——回测工具输出数字，评审包输出**可以签字的证据**。见 4.5 第 7 项。

### 5.3 策略作者（Author）🔜
**从目标生成候选策略，而不只是调现有策略的阈值。**
- 一级：生成 `policy_overrides` 组合（今天已经能做）
- 二级：生成 Python 策略代码 → 沙箱验证 → 回测 → 审稿。这就是你之前想的 Strategy Authoring Copilot
- 前提：沙箱升级。LLM 写的代码不能跑在当前的 demo 级隔离里

### 5.4 监控（Monitor）🔜
**每月新数据到了自动重跑冠军**：PSI 漂移超阈值 → 自动开一个调查会话 → 给出"要不要重新校准"的建议。这是 Risk Operations Agent，需要时间轴数据（第 4 节的根本问题）。

### 5.5 MCP server 🔜
把 `tools.describe()` 包成 MCP server，Claude Code / Cowork 能直接指挥平台做实验。工具层已经是自描述的，工作量小。

### 什么不该让 Agent 做
- **上线**。永远是人的动作。Agent 最远推进到评审包。
- **自定义指标口径**。指标定义冻结在 `METRIC_VERSION`，Agent 不能发明新指标。
- **越过环境边界下结论**。`not_valid_for` 是硬约束。
