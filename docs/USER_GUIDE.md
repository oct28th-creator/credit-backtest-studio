# BackTest Studio 使用手册

> 面向第一次用信贷回测平台的人。不需要风控背景，读完能独立跑实验、看懂结果、知道什么时候不该相信结果。
> 文中所有数字都是默认样本（consumer_2024q1q2，8 万行合成账簿，seed=42）上的**实测值**，不是举例。
> 对应版本：`feat/agentic-p3` @ `a32e314`

---

## 1. 这个平台在干什么

一句话：**拿同一批历史客户，重新跑一遍不同的审批策略，看谁批得更好。**

信贷审批策略就是一套"批不批、批多少"的规则 + 模型。换策略是有风险的动作——批松了坏账上来，批紧了生意做不成。回测就是在不动真钱的前提下，先在历史数据上比一比。

三个角色，理解这三个词就够了：

| 角色 | 含义 |
|---|---|
| **Champion（冠军）** | 当前线上跑着的策略，基线。默认 v2.2 |
| **Challenger（挑战者）** | 想替换冠军的候选。默认 v2.3 |
| **Beta** | 更早期的试验版本，通常更激进。默认 v2.4-Beta |

默认四套内置策略，都是"黑五大促提额"场景：

| 版本 | 通过率 | 坏账率(MOB12) | RAROC | 特点 |
|---|---|---|---|---|
| v2.2 冠军 | 22.7% | 1.53% | 19.7% | 保守基线，稳定跑了 18 个月 |
| v2.3 挑战者 | 43.5% | 1.76% | **23.9%** | 重训模型，通过率接近翻倍而坏账几乎没动 |
| v2.4-Beta | 65.8% | 3.72% | 20.5% | 激进，18-25 岁客群有公平性问题 |
| v2.5-RC | 48.8% | 2.38% | 22.6% | 图网络反欺诈 |

看这张表就能感觉到回测在回答什么：v2.3 通过率从 23% 提到 44%，坏账只涨了 0.2 个点——**这是真的吗？哪来的？可持续吗？** 后面每一层指标都在回答这个问题的一个侧面。

## 2. 五分钟跑通第一次实验

```bash
cd ~/Documents/Qoder/credit-backtest-studio
bash scripts/ctl.sh start
```

一条命令拉起前后端（后台运行，等后端健康检查通过才起前端）。常用的几个：

| 命令 | 干什么 |
|---|---|
| `ctl.sh start` / `stop` / `restart` | 起 / 停 / 重启。**改了 `.env` 或依赖后用 restart** |
| `ctl.sh status` | 谁在跑、健康不健康、AI 通没通 |
| `ctl.sh logs api` | 跟踪日志（`api` \| `web`） |
| `ctl.sh doctor` | 体检：依赖、端口、健康、**是否在跑假数据** |
| `ctl.sh test` | 跑后端 + 前端测试 |

端口冲突：`API_PORT=8001 WEB_PORT=5174 bash scripts/ctl.sh start`

浏览器打开 http://localhost:5173。

**第 1 步｜配置页**
左边选 Champion / Challenger / Beta 和样本，右边有两张卡片：
- **样本信息**：这批数据多少行、什么时间窗
- **仿真环境**：先保持默认「历史回放」，第 5 节再讲另一个

也可以直接在顶部输入框用自然语言描述（需要配 DeepSeek key），比如「对比 v2.3 和 v2.2 在 18-25 岁客群的表现」。

**第 2 步｜点「运行回测」**
几秒钟，8 万行数据跑完 L1–L5 全部指标。

**第 3 步｜结果页**
顶部信息条给你四个关键身份信息：样本、样本量、**run_id**、**snapshot_sha**。下面是仿真环境卡片和**可信度卡片**（第 4 节），再下面是切片筛选器，最下面是 L1–L5 五个标签页。

**第 4 步｜切一刀试试**
切片筛选器选「年龄段 = 18-25」，页面重算。注意看顶部——**run_id 变了**。这是设计如此，第 11 节解释。

> ⚠️ **如果页面顶部出现橙色的「演示数据」横幅**，说明前端没连上后端，你看到的所有数字都是假的。跑 `ctl.sh doctor` 看是哪一环断了。这个横幅是故意做得很显眼的——在信贷工具里，编造的数字和实测的数字长得一模一样是不可接受的。

## 3. 看懂结果页：L1–L5 五层

五层不是五个报表，是五个逐步收紧的问题。前一层过不了，后一层的数字没有意义。

### L1 模型质量：模型分得清好人坏人吗？

| 指标 | 大白话 | 怎么算好 |
|---|---|---|
| **KS** | 好人和坏人的分数分布拉开了多远 | 0.3 以上可用，0.4 以上不错 |
| **AUC** | 随机拿一个坏人一个好人，模型把坏人排在前面的概率 | 0.5 = 瞎猜；0.7 可用；0.75+ 好 |
| **Brier** | 预测概率准不准（不只是排序对不对） | 越小越好 |
| **排序单调性** | 分数从低到高，坏账率是不是真的一档比一档高 | 出现反转 = 分数在那一段没有意义 |
| **PSI** | 这个月的客群和基期比，漂移了多少 | <0.1 稳定 / 0.1–0.25 观察 / >0.25 报警 |
| **CSI** | 具体是哪个特征在漂 | 同上 |

实测：v2.2 KS=0.309 AUC=0.702；v2.3 KS=0.338 AUC=0.720。

**常见误读**：AUC 高 ≠ 能赚钱。模型只负责排序，赚不赚钱看你在哪里切一刀（cutoff），那是 L2 的事。

### L2 商业价值：这套策略赚不赚钱？

| 指标 | 大白话 |
|---|---|
| **通过率** | 100 个申请批了几个 |
| **坏账率** | 批出去的人里最后坏了几个 |
| **户均利润** | 每批一户平均挣多少 |
| **RAROC** | 风险调整后收益。挣的钱扣掉预期损失，再除以占用资本 |

页面上除了比率还有**规模化数字**（核准户数、总敞口、总利润、预期损失、经济资本）。比率回答"划不划算"，规模回答"值多少钱"——v2.3 比 v2.2 多批 16,651 户，这个数才是决策要签字的东西。

**为什么看 RAROC 不看利润**：多批一定多挣绝对额，但可能是拿更多资本和更多风险换来的。RAROC 把这三件事放在一个分母上比。

**常见误读**：通过率和坏账率必须一起看。单看「v2.4-Beta 通过率 65.8%」是漂亮的，配上「坏账 3.72%，是冠军的 2.4 倍」就不一定了。

### L3 风险：放出去的钱，坏得多快？

- **Vintage 曲线**：同一批客户放款后第 1、2、3……12 个月的累计坏账。曲线越晚翘头越好。
- **Roll rate（迁徙率）**：M1→M2→M3+ 的恶化比例。看逾期客户是自己好转还是继续烂下去。
- **FPD**：首期就逾期。这个高通常不是风险问题，是欺诈或者进件质量问题。

这一层现在是**实测的**：合成账簿带时间轴（放款月份、首次逾期 MOB、逾期阶段），vintage、迁徙率、FPD 都是从账户级明细数出来的，不是坏账率的函数。如果你上传的数据集没有时间列，页面会标注「派生」——那种情况下这一层只是 MOB12 的换算，别当独立证据用。

**常见误读**：坏账率是一个"截止到今天"的快照。新放的款还没到暴露期，天然好看。Vintage 就是为了消除这个错觉。

### L4 Swap-set：整个回测的灵魂

两套策略批的人大部分是重叠的。真正的差异只在两个格子里：

```
                    冠军 v2.2 批  │  冠军 v2.2 拒
                 ─────────────────┼──────────────────
挑战者 v2.3 批  │   双批            │  Swap-in（换入）
                 │   （没差异）      │  ← 挑战者多批的人
                 ─────────────────┼──────────────────
挑战者 v2.3 拒  │  Swap-out（换出） │   双拒
                 │  ← 挑战者拒掉的人  │   （没差异）
```

默认样本上的实测：

| 象限 | 户数 | 坏账率 | 怎么读 |
|---|---|---|---|
| Swap-in | 19,456 | **2.34%** | 挑战者多批进来的人，坏账并不高 |
| Swap-out | 2,805 | **4.28%** | 挑战者拒掉的人，本来坏账很高 |

这两个数字合起来才解释了第 1 节那个谜题：**v2.3 通过率翻倍而坏账基本持平，是因为它一边多批了一批相对干净的人，一边把冠军批错的高风险客户挡住了。**

还有两个数：
- **一致率**：两套策略决策相同的比例。太高说明挑战者没什么新意，太低说明它在乱来。
- **p 值**：swap 两侧的坏账差异有多大可能只是运气。**p > 0.05 就不能说"更优"**。

页面上还有一张**归因表**：每一笔 swap 是被哪条规则改判的（评分闸门 / DTI 闸门 / MOB 闸门 / 定价），以及每条规则各自的坏账。这张表是下一节"增量来源分解"的原料。

### L5 公平性：这套策略会不会歧视某类人？

| 指标 | 大白话 | 红线 |
|---|---|---|
| **DI ratio** | 某个群体的通过率 ÷ 参照群体的通过率 | **< 0.8 触线**（四分之五规则） |
| **TPR gap** | 不同群体之间"该批的批到了"的比例差 | 差异越小越好 |
| **特征重要性** | 模型主要靠什么在判断 | 出现受保护属性 = 严重问题 |

默认样本实测（young_core = 18-25 岁 vs 26-55 岁）：

| 策略 | female_male | outsider_local | young_core |
|---|---|---|---|
| v2.2 冠军 | 0.984 | 0.992 | **0.796** ← 已经压线 |
| v2.3 挑战者 | 1.012 | 0.987 | 0.839 |
| v2.4-Beta | 0.999 | 1.003 | **0.534** ← 明显触线 |

注意一件容易被忽略的事：**触线的是现役冠军 v2.2**。挑战者反而把这一项改善了（0.796 → 0.839）。默认这一跑的评审结论是"不可推进"，原因不在挑战者身上，在基线身上——这正是评审包（第 4 节）要说清楚的东西。

**为什么这层必须看**：性别不是模型输入，但通过率照样可能出现组间差异——因为负债率、工作年限这些变量本身和人群分布相关。这叫间接歧视，只能靠 DI 这类指标测出来。

## 4. 结果页上的三张卡片

L1–L5 告诉你**数字是多少**。这三张卡片回答的是另外三个问题：这个增量**从哪来**、这个结果**能不能信**、以及**怎么拿去评审**。

### 4.1 增量来源分解（L4 下方）

"同样坏账率下多批一倍"在拆开之前不是结论。多批的人可能是**模型变准**换来的（旧模型误杀、新模型重新排序），也可能是**闸门放松**换来的（DTI 从 0.65 放到 0.70）。这两条路径走完全不同的审批流程。

卡片直接给出一句话结论，是从归因表算出来的算术，不是叙述：

> 增量的 **84%** 来自模型区分度提升（被旧模型评分拦下、被新模型重新排序的客群），只有 16% 来自政策放宽；换入客群坏账 2.34%，换出客群坏账 4.28%，即多批的比拒掉的更干净。**这条路径按模型升级审批，不按政策放松审批。**

下面配一条 84% / 16% 的色带和逐规则明细。如果哪天这个比例翻过来（政策驱动占多数），卡片会变成琥珀色——这就是提醒你换审批路径的信号。

### 4.2 可信度卡片

这张卡片跑的是**和 Agent 的 Critic 完全同一套确定性红线**。给人看的和给模型看的必须是同一套判定，否则"你信页面还是信 Agent"就成了一个真问题。

卡片头部一个标签：`无阻断` / `有提示 · N` / `被阻断 · N`。展开后每一条红线一行，带具体数值。

三个按钮：

- **一键复现**：同配置换 3 个种子重跑，返回均值 / 标准差 / 95% 置信区间，以及最关键的一项——**排序有没有翻转**。翻转了说明这个差异来自抽样，不是策略差异。
- **找修复**：只对"有旋钮可拧"的红线出现（DI、坏账上限、核准户数）。它会自动搜索一条能清掉这条红线的阈值路径，每次尝试都是一个真实的 run（可点开），并且回答两件事：清掉了没有、**有没有引入新的阻断项**。同时给一张诊断表：这个群体是被哪条规则卡住的、和参照群体差多少个百分点。
  > 只对能修的红线给按钮。`protected_attribute_as_input`（受保护属性入模）没有按钮——给它一个按钮等于承诺一个不存在的修复。
- **下载评审包**：见下。

### 4.3 评审包（Evidence Bundle）

一个 Markdown 文件，装的是策略上线评审需要的全部东西：候选 run 及其 manifest、红线报告、多种子复现结果、拒绝推断的方法误差、增量归因表、审稿意见，以及——**这一包没有回答的问题清单**。

默认这一跑的输出：

```
结论：不可推进
理由：存在 2 项阻断级红线，必须先解决

本包没有回答：
· 未做多种子复现：本结论仍基于单次抽样
· 历史回放环境：拒绝客群无表现数据，放开准入后的客群变化未被验证
· 无行为反馈仿真：接受率、用信率随额度变化的影响未被建模
```

三档结论只有 **不可推进 / 证据不足 / 可提交人工评审**。**没有"可以上线"这一档**——上线永远是人的动作，平台最远推进到"可以拿去评审"。

如果你在下载前先点过「一键复现」，包里会带上复现结果，"本包没有回答"里那一条会自动消失。

## 5. 仿真环境与拒绝推断（这个平台最值钱的部分）

### 先理解这个行业最大的坑

回测有个致命的结构性问题：**你只知道你批过的人后来还没还钱。被拒掉的人，你永远不知道他们本来会怎样。**

所以"挑战者多批的这两万人坏账率 2.34%"——这个数在真实生产环境里根本测不出来，只能估。行业标准做法叫**拒绝推断（Reject Inference）**。

### 这个平台做了什么不一样的事

合成账簿里所有人都有真实标签，所以直接做拒绝推断毫无意义。平台反过来用：

1. **先遮蔽**冠军拒绝掉的那 6 万多人的表现数据（还原真实生产条件）
2. 用各种方法**估回来**
3. 拿被遮蔽的真值**反算这个方法错了多少**

第 3 步是关键。每家机构都在做第 2 步并把结果当测量值汇报，几乎没人报第 3 步。

### 怎么用

配置页 → 仿真环境 → 选「拒绝推断（L0b）」→ 选方法 → 运行。结果页顶部环境卡片展开：

| 方法 | v2.3 swap-in 估计坏账 | 真实坏账 | 偏差 | 相对误差 |
|---|---|---|---|---|
| 忽略拒绝客群 | 0.00% | 2.34% | −2.34pp | 100%（结构性低估） |
| 差额分摊（行业惯用 ×2 惩罚） | ~4.1% | 2.34% | +1.8pp 左右 | **80% 上下** |
| 模糊赋权 / 反向加权 | 用 `compare_ri_modes` 一次比完 | | | |

**这张表的意思是**：行业里最常用的 parceling 方法，在这份账簿上把新客群的风险高估了近一倍。如果你拿这个数去做额度政策决策，你会因为一个方法误差而错过一个本来成立的策略。

一次比完四种方法（不用跑四次回测）：

```bash
curl -s -X POST localhost:8000/api/agent/tools/compare_ri_modes \
  -H 'content-type: application/json' \
  -d '{"args":{"config":{"champion":"v2.2","challenger":"v2.3","sample_id":"consumer_2024q1q2"}}}'
```

相对误差超过 50% 时，`reject_inference_unreliable` 直接变成阻断级红线——方法误差比它声称的效应还大，这个结果不能用。

### 环境会告诉你它不能回答什么

每个环境都自带 `not_valid_for` 清单，直接显示在结果页：

- **历史回放（L0a）** 不能回答：放开准入后新客群的表现、长期客群迁移、任何依赖客户对政策做出反应的问题
- **拒绝推断（L0b）** 不能回答：行为反馈（接受率/用信率随额度变化）、多期滚动、精确到小数点后一位的坏账预测

这不是免责声明，是硬约束：超出环境能力的结论会被红线拦下来。

## 6. 调策略旋钮：不换策略，只挪阈值

内置策略允许调六个旋钮（白名单，其他一律报错——能挪阈值，不能重新定义策略）：

`target_approval_rate`（目标通过率）· `dti_limit`（负债率上限）· `mob_months`（观察期）· `mob_dpd_max` · `score_cutoff` · `limit_increase_min/max`

**一次扫一条曲线**（服务端展开，不用调 N 次）：

```bash
curl -s -X POST localhost:8000/api/agent/tools/sensitivity_scan \
  -H 'content-type: application/json' \
  -d '{"args":{"base_config":{"champion":"v2.2","challenger":"v2.3","sample_id":"consumer_2024q1q2"},
       "strategy":"v2.3","knob":"target_approval_rate","values":[0.3,0.4,0.5,0.6]}}'
```

每个点都是一次独立、可引用、可复现的 run。这条曲线就是"通过率-收益"的权衡曲线，找拐点用。

## 7. 这是结论，还是运气？

一次回测只是一次抽样。「v2.3 的 RAROC 比 v2.2 高 4 个点」可能是策略的性质，也可能只是这一份样本的性质。

页面上点「一键复现」就行；命令行等价物：

```bash
curl -s -X POST localhost:8000/api/agent/tools/replicate_across_seeds \
  -H 'content-type: application/json' \
  -d '{"args":{"config":{"champion":"v2.2","challenger":"v2.3","sample_id":"consumer_2024q1q2"},"n":3}}'
```

返回每个指标的均值、标准差、95% 置信区间，以及最关键的一项：**排序在不同种子下有没有翻转**。

翻转了 = 这个差异来自抽样，不是策略差异。平台会直接把结论判为 `not_supported`，置信度封顶 0.25，不给解释的余地。

## 8. 让 Agent 自己跑一轮

左侧「Agent 调查」页，输入一个问题，看它分阶段实时跑完。命令行：

```bash
curl -s -X POST localhost:8000/api/agent/investigate \
  -H 'content-type: application/json' \
  -d '{"goal":"v2.3 放宽通过率后 RAROC 是否还优于 v2.2",
       "base_config":{"champion":"v2.2","challenger":"v2.3","sample_id":"consumer_2024q1q2"},
       "budget":{"max_experiments":5}}'
```

六个阶段，每步都在返回的 `events` 里：

| 阶段 | 干什么 |
|---|---|
| `prior_work` | 先查有没有人问过同样的问题（查得到就不重复烧算力） |
| `plan` | 把目标翻译成一组可证伪的实验，必须含基线对照 |
| `experiment` | 逐个执行，走和你点按钮完全相同的代码路径 |
| `guardrails` | 确定性红线检查，**在任何叙述产生之前** |
| `findings` | 读紧凑指标表给发现 |
| `replication` | 花剩余预算做多种子复现 |
| `critique` | 对抗性审稿：样本量、多重比较、单一种子、公平性、环境边界、过拟合 |

**为什么要拆成 Analyst 和 Critic 两个角色**：同一个模型既找结论又验证结论，它一定会验证通过。Critic 拿到的 guardrail 报告是**不可推翻的事实**——有阻断项，verdict 强制降为 `not_supported`，置信度封顶 0.3。

没配 DeepSeek key 也能跑，三步都有确定性兜底（默认计划 = 基线 + 通过率扫描）。配了 key 才有真正的假设生成和归因分析。

**预算是在工具层强制的，不是在提示词里劝的。** 说服不了它。

## 9. 历史页：实验日志 / 实验树 / 两次对比

因为 run 不可变（第 11 节），一个问题往往会长出好几个 run：原始提交 → 切片 → 找修复的几次尝试 → 复现。流水账是错的形状，所以历史页有三个视角。

### 9.1 实验日志

流水，最新在上。除了 KS/AUC/RAROC，**每一行都带红线判定**：`无阻断` / `有提示` / `被阻断`，鼠标停上去看具体是哪几条。

一个不能上线的 run 不该跟能上线的长得一样——这是这一列存在的全部理由。

### 9.2 实验树

同一个 `root_run_id` 的 run 收成一条**线索**，按父链缩进：

```
● a1b2c3d4-e5f   无阻断   通过率 43.5% · 坏账 1.76% · RAROC 23.9%
  └ f6g7h8i9-j0k  被阻断·1   切片 age_band=18-25   通过率 38.1% …
    └ k1l2m3n4-o5p  无阻断     参数覆写 v2.3.dti_limit=0.62 …
```

线索层面直接告诉你：这条线索问的是什么（hypothesis）、最后的结论是什么（conclusion）、里面几个被阻断几个干净。

这就是"找修复"按钮点完之后你该来的地方——每次尝试都是树上一个节点，能看到它是从哪个 run 派生的、拧的哪个旋钮。

### 9.3 两次对比

在日志或树里给任意两行分别按 **A** 和 **B**，点「对比这两次」。

两个刻意的设计：

- **按角色对齐，不按版本号。** A 的挑战者对 B 的挑战者，A 的冠军对 B 的冠军。如果按版本号匹配，一次角色互换的实验就会让你读出完全相反的结论。
- **配置差异印在指标差异上面。** 不知道哪个输入动了（种子？切片？旋钮？），指标差值没有意义。两个 run 的 manifest 完全一致时，页面会直接说：输入相同，任何差值都是引擎 bug。

指标按 L1 / L2 / L3 / L5 分组，每行给 A 值、B 值、差值和"谁更优"。**通过率那一行永远没有优劣**——它只跟坏账率一起看才有方向，页面拒绝替你下这个判断。

## 10. 红线表：什么时候不该相信结果

**阻断（结论不可用）**

| 代码 | 触发条件 | 为什么 |
|---|---|---|
| `disparate_impact` | 任一群体 DI < 0.80 | 四分之五规则，合规红线 |
| `approved_book_too_small` | 核准户数 < 500 | 坏账率没有统计意义 |
| `protected_attribute_as_input` | 上传策略把性别/种族等作为模型输入 | 直接违规 |
| `reject_inference_unreliable` | 推断方法相对误差 > 50% | 方法误差比它声称的效应还大 |

**警告（结论成立，但必须带着这个说）**

`swap_not_significant`（p > 0.05）· `rank_ordering_broken`（分数段坏账出现反转）· `bad_rate_ceiling` · `weak_discrimination`（AUC < 0.6）· `thin_sample`（样本 < 5000）· `extreme_override`（目标通过率 > 90%）· `replay_only_environment` · `reject_inference_noisy`

红线是确定性代码算出来的，不是模型判断的——所以模型说服不了它，你也说服不了它。

还有一条容易被忽略的规则：**缺失的指标不等于零指标**。某个策略没有 L2 数据时，校验会跳过它，而不是判它"通过率 0% 触线"。

## 11. 为什么切片之后 run_id 变了

因为**每个 run 都是不可变的证据**。

切片、换种子、调旋钮，都会产生一个**新的 run**，通过 `parent_run_id` / `root_run_id` 挂在原来那个下面。原来的 run 一个字都不会被改。去实验树（第 9 节）看这条线索长什么样。

原因很直接：Agent 会引用 run_id 作为结论的证据。如果昨天引用的 run_id 今天指向了另一份数据，整条证据链就废了。

三个 ID 的分工：

| 字段 | 是什么 |
|---|---|
| `run_id` | 这次运行的身份 |
| `manifest_sha` | **复现哈希**：把所有会影响数值的输入（数据内容、策略代码、种子、旋钮、切片、环境、指标版本）折成一个 SHA-256 |
| `snapshot_sha` | 旧版短哈希，保留兼容 |

不变式：**相同 manifest_sha ⇒ 相同数值**。所以提交实验时平台会顺手告诉你「这个实验之前跑过，run_id 是 xxx」，直接复用不重算。

```bash
curl -s localhost:8000/api/experiments/<run_id>/manifest   # 你是怎么算出来的
curl -s localhost:8000/api/experiments/<run_id>/lineage    # 这条实验线索上都有谁
```

## 12. 上传自己的策略：沙箱的边界

策略页可以上传 Python 策略（实现 `score()` 和 `approve()`，声明 `STRATEGY_META`）。上传的代码跑在一个**隔离子进程**里，边界如下。

**能用**：numpy、pandas、scipy、sklearn 这些计算库，以及正常的 Python 语言特性（class、继承、`type`/`object`/`super` 都可以）。

**不能用**：

| 拦住什么 | 怎么拦的 |
|---|---|
| 读写任何文件 | `open` 从内建里删掉，子进程里连 `builtins.open` 本身都关了 |
| 联网 | `socket` 关掉 |
| 动态执行代码 | `eval` / `exec` / `compile` / `__import__` 全部移除 |
| 绕过隔离的经典手法 | 上传即 AST 扫描，所有 dunder 属性（`__class__`、`__subclasses__`、`__globals__`…）一律拒绝 |
| 跑死机器 | CPU 6 秒、内存 1 GiB、写盘 4 MiB 的硬上限 |

被拒时报错会告诉你具体是哪一行的哪个东西不允许。

**为什么这么严**：`backend/.env` 里放着你的 API key。在加固之前，一段上传的策略可以 `open('backend/.env').read()`，把 key 编码进它返回的 float 数组带走——这条路现在是堵死的。这也是后面"让 AI 写策略代码"那一步的前提：能自动生成代码，就必须假设代码不可信。

## 14. 三条上手路线

**10 分钟｜先建立直觉**
1. 默认配置跑一次
2. L2 看三行通过率和坏账，注意"规模化数字"那一栏
3. L4 看 swap-in / swap-out 两个格子——理解 v2.3 为什么能"又松又稳"
4. 看 L4 下方的**增量来源分解**：84% 来自模型，不是放松政策
5. 切片到 18-25 岁，回 L5 看 v2.4-Beta 的 DI 掉到 0.534

**30 分钟｜理解可信度**
6. 展开**可信度卡片**，看默认这一跑为什么被阻断（是冠军 v2.2 的 DI=0.796，不是挑战者）
7. 点「一键复现」，看排序稳不稳
8. 对 `disparate_impact` 点「找修复」，看它搜出来的阈值路径和诊断表
9. 下载**评审包**，重点读最后那段"本包没有回答什么"
10. 换成拒绝推断环境跑一次，展开误差表；`compare_ri_modes` 一次比完四种方法

**深水区｜让 Agent 干活**
11. `/api/agent/investigate` 或「Agent 调查」页跑一轮，重点读 `guardrails` 和 `critique` 两段
12. 故意给一个会踩红线的目标（比如把 v2.4-Beta 当挑战者），看它怎么被拦下来
13. 去**实验树**看这一轮生出了多少个 run，挑两个做**对比**

## 16. 常见问题

**页面顶部有橙色「演示数据」横幅？**
前端没连上后端，页面上所有数字都是假的。`ctl.sh doctor` 看哪一环断了；`ctl.sh logs api` 看后端报什么。

**AI 解读面板没反应？**
没配 key。在 `backend/.env` 里填 `DEEPSEEK_API_KEY`，然后 `ctl.sh restart`。Agent 闭环不配也能跑（走兜底），但 AI 解读和自然语言配置需要。

**改了依赖 / .env 之后怎么办？**
`ctl.sh restart`。脚本会检查 `requirements.txt` 的时间戳，变了就自动重装依赖——之前"少装一个包导致后端起不来"的坑就是这么堵上的。

**端口被占用？**
`API_PORT=8001 WEB_PORT=5174 bash scripts/ctl.sh start`

**回测跑得慢？**
第一次要生成 8 万行数据并标定各策略阈值，之后有缓存。同配置重复提交会直接命中 manifest 缓存，秒回。

**为什么默认这一跑就"不可推进"？**
因为现役冠军 v2.2 在 18-25 岁客群上 DI=0.796，压在四分之五规则线下。这不是挑战者的问题——挑战者反而把它改善到 0.839。评审包会把这个事实摆出来，而不是替你把它藏起来。

**这些数据是真的吗？**
不是。是按信贷业务逻辑生成的合成账簿（评分、负债率、多头、放款月份、逾期表现之间保持真实的相关结构），用于演示和方法验证。所有指标都是真算出来的，不是硬编码。

**能用自己的数据吗？**
可以。数据集页上传 CSV，做列映射，策略页上传自己的 Python 策略。两个注意：上传数据集没有真值列，拒绝推断的误差标定用不了，只能跑历史回放环境；没有时间列的话 L3 会标注「派生」，那一层不能当独立证据。
